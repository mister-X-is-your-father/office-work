## 1. 真因フレーム（確定版・本人承認 2026-07-06）

計画という機能が「どこで壊れているか」を機能分解した3点を正とする。

| 記号 | 機能 | 壊れ方 |
|---|---|---|
| **A** | 立てる | 具体的な計画が立てられていない |
| **B** | 守る | 立てた計画が守られない |
| **C** | 軌道修正 | 崩れたあと立て直されない |

### 診断

- **震源 = A。** 計画の発火条件を「目の前が片づいたら、腰を据えて」に設定している。だがその状態は直近半年でほぼ来ていない（本人確認）。差し込みと小タスクが無限に補充されるため、この条件は構造的に永遠に満たされない。加えて「腰を据えて＝重い計画」というイメージが、15分で済む軽い計画すら着手させない。**能力ではなく発火条件の設定ミス。**
- **生命線 = C。** 計画が崩れたときの応答が「頑張る」＝軌道修正の代替品。気合いで今日を乗り切れてしまうため組み直しが一度も必要にならず、見積もりは校正されず、差し込み量は測られず、「計画は崩れるもの」という不信だけが積み上がる。**学習ループの死。**
- **B は大部分が症状。** 崩す犯人は ①外部差し込み（環境・ゼロ化不能→バッファで吸収。その設計にはCの実測データが必要）②タスク膨張（A未分解 × C未校正の産物）③自分発差し込み（唯一の独立成分・行動癖）。
- **ループ構造:** A不発 → 未分解タスクが膨張しB崩壊 → 頑張るで吸収（C不発・残業でメタ時間がさらに消える）→ データも計画信頼も増えないまま A不発が深まる。
- **原理:** 外部差し込みが消せない以上「崩れない計画」は存在しない。計画は守り切るものではなく、崩れては直すもの。システムの持続性を決めるのは C。

### 旧真因（#783 hisho ヒアリング）との対応（レイヤー違い・併存）

| 旧真因 | 本フレームでの位置 |
|---|---|
| メタ作業の不在 | A と C が業務として存在しない理由 |
| 即時達成感ドリブンの報酬系 | 「実務優先」と「頑張る」を毎回選ばせるエンジン |
| 自分発差し込み | B の独立成分 |

### 第4の論点「選ぶ」（第2フェーズ）

A/B/C サイクルは「何を計画に積むか」に無関心。運営業務に時間が向かない問題（6月分析の核心）はこの「選ぶ」レイヤーに属し、本プロジェクトのスコープ外。
**解決の形:** 「計画する・運営する」という行為自体を計画の項目として積む。第1歩＝朝15分・週30分でメタ作業がカレンダー項目になること。第2フェーズ＝実測でキャパが数字になった後、運営業務の枠を計画に正式に積む。

## 2. 課題（#784 確定・根治/対症の区別つき）

1. **[根治A] メタ作業の業務化** — 毎朝15分の段取り＋週30分の予実振り返りを定例化。完了条件: カレンダーブロックが存在し、実施率80%以上を2週間連続。
2. **[根治A] 分解の前払いルール** — 見積4h超は着手前に「最初の30分でやること」を明文化。完了条件: 週次レビュー時点で未分解の大タスク0件。
3. **[根治B] 自分発差し込みの隔離** — 改善ネタは即着手禁止→書き溜めに記録し週次で選別着手。完了条件: 週次で自分発差し込み件数が数字で見える。
4. **[対症] 差し込み量の実測** — 2週間、件数・時間・発生源を記録。完了条件: 発生源別の内訳時間が出てバッファ値に反映。

## 4. 朝15分の型（9:00–9:15 固定・タイマー厳守）

主役は A。C の小掃除で始まり、B の仕込みで終わる。

| # | 工程（所要） | フェーズ | 内容 |
|---|---|---|---|
| 1 | 持ち越し判定（2分） | **C 軌道修正**（日次小口） | 昨日の未完了を「今日やる／後日へ／捨てる」に振り分け |
| 2 | 正味キャパの数値化（2分） | **A 立てるの土台 ＋ B 仕込み** | 定時まで − 会議・定例 − 差し込みバッファ（仮1.5h→7/17実測値）＝今日積めるh。数字を1個書く |
| 3 | 積む＆捨てる（6分） | **A 立てる本体 ＋「選ぶ」日次版** | 正味hに収まる分だけ選び順番を決める。溢れは「今日はやらない」と明示（最重要）。計画・運営系もここで枠入れ |
| 4 | 初動30分の明文化（4分） | **A 立てる ＋ B 予防** | 今日着手の重いタスク（4h超目安）に「最初の30分でやること」を1行。全部は分解しない |
| 5 | 差し込み記録の準備（1分） | **B 観測装置**（→C の弾薬） | 実測欄を開く。発生時は1行15秒 |

**原則:** 15分を超えそうなら計画中に実務を始めているサイン。書き先は日次タスクシート1箇所のみ。

## 5. 週30分の型（毎週金曜 13:00–13:30）＝ C 本体

「頑張る」を「組み直す」に置換する定例。

1. Claude Code に予実集計を出させる（下記プロンプト・負荷ゼロ化）
2. 見積ズレ上位3件だけ見る
3. 差し込み実測を眺めてバッファ値を更新
4. 改善ネタ書き溜めから来週分を選別（課題3連動）

### Claude Code 予実集計プロンプト（初回7/10に検証）

> タスクシートの今週分（月〜金）について: ①タスク別の見積h/実績h/差分の表 ②差分が大きい上位3件と推定理由ひと言ずつ ③差し込みの件数と合計時間を発生源別に ④未完了で来週へ持ち越すタスク一覧。表のみ・簡潔に。

検証観点: 下書きが5分以内に出るか／数字が合っているか。合格なら毎週貼るだけで記録負荷ゼロ。

## 8. 目標管理シート記入文面（v2.1・#786）

**タイトル:** タスク運用の立て直し — 計画サイクル（立てる・守る・直す）の業務化と差し込みの定量管理

**背景・現状課題:** 計画を「立てる→守る→崩れたら直す」のサイクルが業務として機能していなかった。立てる行為は「目の前が片づいたら」と先送りされ続け、崩れた計画はその場の頑張りで吸収されて組み直されず、見積精度が上がらない悪循環にあった。個人の意志ではなく仕組み（カレンダー化・ルール化・実測）でサイクルを業務に組み込む。

**行動目標（判定可能な形式）:**
1. （立てる・直す）毎朝15分の段取り（9:00–9:15・当日の正味稼働hを数値で決めてからタスクを積む）と週1回30分の予実振り返り（金13:00–13:30・見積乖離の確認・バッファ更新）をカレンダーブロックとして常設し、実施率80%以上を2週間連続で達成（7/17判定）。以降、上期末まで実施率80%を月次で維持。
2. （立てる）見積4h超のタスクは着手前に「最初の30分でやること」を明文化する運用を定着。週次レビュー時点の未分解大タスク0件を維持。
3. （守る）差し込みを発生源別（外部／チーム／自分発）に2週間実測し、内訳時間を日次計画のバッファ値に反映。自分発の差し込みは即着手0件（書き溜めリスト経由100%）を維持。

**課長対策:** 「立てる・守る・直す」の3機能フレームは仕組み・再発防止派に通りやすい構造（症状の列挙ではなくサイクルの故障箇所を特定→各箇所に仕組みを当てる）。すべて「実施率80%」「0件」「100%」の判定可能形式・精神論なし・残業絶対値なし。根拠を問われたら: 実施率80%＝週5日中4日（差し込み1日分の余裕込みの現実値）、2週間＝差し込み実測期間と同期。
