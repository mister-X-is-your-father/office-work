## ADR-001: タスクの箱に Vikunja を採用

**状態**: 採用 (2026-06)

**背景**: OSS PM/タスクツール5つを評価した（OpenProject / Orangescrum / Tuleap / Vikunja / WeKan）。要件は ガント＋カンバン＋時間/コスト追跡＋**人別キャパ可視化**、チーム2〜4名、データ主権。

**検討した選択肢**:
- **OpenProject** — OSS総合力トップ。ガントが本格的。が重い。人別キャパは半手動。
- **Orangescrum** — リソースヒストグラムがキャパ要件に最も近い。**だが開発停止（2022・PHP5.6・5ユーザー上限・未修正CVE）** で採用不可。
- **Tuleap** — アジャイル特化、バーンダウン等は強い。**ガント・時間キャパが中心でなく弱い**。重い（~4GB）。
- **WeKan** — 純カンバン。ガント・キャパなし。
- **Vikunja** — list/kanban/gantt/table、**モダン・軽量・API良好・OSS（AGPL）**。人別キャパ専用ビューは無い。

**決定**: **Vikunja** を「タスクの箱」として採用し、不足する人別キャパ可視化は自前で足す。

**理由**: 2〜4名に身軽でちょうどよく、**APIとデータが綺麗**で自前レイヤーを載せやすい。キャパ機能はどのOSSも弱いので、土台は「拡張しやすさ」で選ぶのが合理的。重厚なOpenProjectより保守が軽い。

**結果**: キャパ/着地/トリアージ等は自前レイヤーで実装する前提に（[ADR-002](#adr-002)）。

## ADR-002: キャパ層は Vikunja を fork せず API 越しのオーバーレイで実装

**状態**: 採用 (2026-06)

**背景**: 「Vikunja改造でいい（Vikunja単体では補えないから）」という要望。改造の度合いに2通りある。

**検討した選択肢**:
- **A. Vikunja 本体を fork** して画面に見積り時間欄やキャパビューを生やす — 自由度は高いが、**本家アップグレードへの追従が事実上死ぬ**・保守コスト大。
- **B. API 越しのオーバーレイ**（本体無改造）で、別アプリとしてキャパ層を載せる — Vikunja標準機能（ラベル等）だけで工数も持てる。

**決定**: **B（API越しオーバーレイ）**。Vikunja 本体のコードは触らない。

**理由**: 「重要ライブラリは abstraction 越しに使う／車輪の再発明をしない」という規範に一致。アップグレード追従を保てる。見積り時間は Vikunja のラベルで表現できるため、本体改造は不要（[ADR-003](#adr-003)）。

**含意**: もし将来「Vikunjaの画面自体に入力欄を生やす」レベルの本体改造が要るなら、別途 ADR を切って判断する。

## ADR-003: 見積り時間は Vikunja のラベルで持つ（`est:4h`）

**状態**: 採用（暫定） (2026-06)

**背景**: キャパのバー長＝各タスクの「時間」が要る。**Vikunja にはネイティブの見積り時間フィールドが無い**（start/end・担当・優先度・進捗%はある）。

**検討した選択肢**:
- **A. ラベルに持たせる**（`est:4h`、またはタイトル末 `[4h]`）をパース — 追加入力は要るが正確。Vikunja標準機能で完結（本体無改造）。
- **B. 期日 start/end から自動日割り** — 入力ゼロだが粗い（実工数とずれる）。
- **C. 別ストア**（Supabase に「タスクID→見積り時間」） — 正確だが二重管理。

**決定**: まず **A（ラベル `est:4h`）**。設定画面（モック17）で `est:4h` ラベル / タイトル末 `[4h]` の解析ルールを選べる想定。

**理由**: 本体無改造（ADR-002）と両立し、精度も確保できる。Bは精度不足、Cは二重管理の保守負担。運用が回ってからBやCの併用を再検討。

**未確定**: ラベル命名規約・複数ラベル時の扱いは実データ接続時に確定する。

## ADR-004: 主画面は「今日の空き容量さがし」を重心に置く

**状態**: 採用 (2026-06)

**背景**: 画面候補は今日/週/総合/プロジェクト等いろいろある。重心をどこに置くか。

**検討した選択肢**: 今日（空きさがし）／ 週プランニング ／ 過負荷検知 ／ 総合ダッシュボード。

**決定**: **今日（日次）の空きさがしを主画面**にする。週・総合・計画は周辺ビューとして配置。

**理由**: チームの一番の困りごとが「今日の差配」。要件 v0.1 の主目的そのもの。総合ビューもまず「今日の空き」を最上段に置く。

**結果**: 「① 運用・今日」に最も多くのモックを割き、採用第一候補も**画面54（縦積み・タスク積み木）**に確定（[02-screens.md](02-screens.md)）。

## ADR-005: モックは静的HTML・サンプルデータ・切り口別ギャラリーで発散させる

**状態**: 採用 (2026-06)

**背景**: 設計確定前に広く案を出したい。

**決定**: フレームワーク無しの**自己完結HTML**（外部依存ゼロ・オフライン描画）で72案を作り、共通サンプルデータで揃え、`index.html` の**切り口別ギャラリー**（ライブiframeサムネ）で一覧する。並列のサブエージェントで生成。

**理由**: 着替えが速く、横並び比較しやすい。GitHub Pages にそのまま載る。実装スタックの決定を遅延でき、発散→収束を分離できる。

**次段**: 収束（本命選定）→ [統合プロトタイプ](03-integration-plan.md) でアプリ化。
