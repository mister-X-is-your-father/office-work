## ADR-001: タスクの箱に TaskStation を採用

**状態**: 採用 (2026-06)

**背景**: OSS PM/タスクツール5つを評価した（OpenProject / Orangescrum / Tuleap / TaskStation / WeKan）。要件は ガント＋カンバン＋時間/コスト追跡＋**人別キャパ可視化**、チーム2〜4名、データ主権。

**検討した選択肢**:
- **OpenProject** — OSS総合力トップ。ガントが本格的。が重い。人別キャパは半手動。
- **Orangescrum** — リソースヒストグラムがキャパ要件に最も近い。**だが開発停止（2022・PHP5.6・5ユーザー上限・未修正CVE）** で採用不可。
- **Tuleap** — アジャイル特化、バーンダウン等は強い。**ガント・時間キャパが中心でなく弱い**。重い（~4GB）。
- **WeKan** — 純カンバン。ガント・キャパなし。
- **TaskStation** — list/kanban/gantt/table、**モダン・軽量・API良好・OSS（AGPL）**。人別キャパ専用ビューは無い。

**決定**: **TaskStation** を「タスクの箱」として採用し、不足する人別キャパ可視化は自前で足す。

**理由**: 2〜4名に身軽でちょうどよく、**APIとデータが綺麗**で自前レイヤーを載せやすい。キャパ機能はどのOSSも弱いので、土台は「拡張しやすさ」で選ぶのが合理的。重厚なOpenProjectより保守が軽い。

**結果**: キャパ/着地/トリアージ等は自前レイヤーで実装する前提に（[ADR-002](#adr-002)）。

## ADR-002: キャパ層は TaskStation を fork せず API 越しのオーバーレイで実装

**状態**: 採用 (2026-06)

**背景**: 「TaskStation改造でいい（TaskStation単体では補えないから）」という要望。改造の度合いに2通りある。

**検討した選択肢**:
- **A. TaskStation 本体を fork** して画面に見積り時間欄やキャパビューを生やす — 自由度は高いが、**本家アップグレードへの追従が事実上死ぬ**・保守コスト大。
- **B. API 越しのオーバーレイ**（本体無改造）で、別アプリとしてキャパ層を載せる — TaskStation標準機能（ラベル等）だけで工数も持てる。

**決定**: **B（API越しオーバーレイ）**。TaskStation 本体のコードは触らない。

**理由**: 「重要ライブラリは abstraction 越しに使う／車輪の再発明をしない」という規範に一致。アップグレード追従を保てる。見積り時間は TaskStation のラベルで表現できるため、本体改造は不要（[ADR-003](#adr-003)）。

**含意**: もし将来「TaskStationの画面自体に入力欄を生やす」レベルの本体改造が要るなら、別途 ADR を切って判断する。

**改訂 (2026-06)**: **実績時間トラッキングに限り、この原則の例外として fork を許可**する（[ADR-006](#adr-006)）。実績時間をコメント解析等の API ハックで持つのは脆弱で破綻するため。fork はその1点に閉じ込め、本体の他部分は引き続き無改造・API越し。

## ADR-003: 見積り時間は TaskStation のラベルで持つ（`est:4h`）

**状態**: 採用（暫定） (2026-06)

**背景**: キャパのバー長＝各タスクの「時間」が要る。**TaskStation にはネイティブの見積り時間フィールドが無い**（start/end・担当・優先度・進捗%はある）。

**検討した選択肢**:
- **A. ラベルに持たせる**（`est:4h`、またはタイトル末 `[4h]`）をパース — 追加入力は要るが正確。TaskStation標準機能で完結（本体無改造）。
- **B. 期日 start/end から自動日割り** — 入力ゼロだが粗い（実工数とずれる）。
- **C. 別ストア**（Supabase に「タスクID→見積り時間」） — 正確だが二重管理。

**決定**: まず **A（ラベル `est:4h`）**。設定画面（モック17）で `est:4h` ラベル / タイトル末 `[4h]` の解析ルールを選べる想定。

**理由**: 本体無改造（ADR-002）と両立し、精度も確保できる。Bは精度不足、Cは二重管理の保守負担。運用が回ってからBやCの併用を再検討。

**未確定**: ラベル命名規約・複数ラベル時の扱いは実データ接続時に確定する。

**改訂 (2026-06)**: 時間トラッキングのために TaskStation を fork する（[ADR-006](#adr-006)）ことになったため、**見積りもラベルでなく `tasks.time_estimate` 実カラムに昇格**する。`est:4h` ラベル方式は fork 後は不要（移行時はラベル→カラムへ一括変換）。ラベル方式は fork しない構成のフォールバックとして本ADRに残す。

## ADR-004: 主画面は「今日の空き容量さがし」を重心に置く

**状態**: 採用 (2026-06)

**背景**: 画面候補は今日/週/総合/プロジェクト等いろいろある。重心をどこに置くか。

**検討した選択肢**: 今日（空きさがし）／ 週プランニング ／ 過負荷検知 ／ 総合ダッシュボード。

**決定**: **今日（日次）の空きさがしを主画面**にする。週・総合・計画は周辺ビューとして配置。

**理由**: チームの一番の困りごとが「今日の差配」。要件 v0.1 の主目的そのもの。総合ビューもまず「今日の空き」を最上段に置く。

**結果**: 「① 運用・今日」に最も多くのモックを割き、採用第一候補も**画面54（縦積み・タスク積み木）**に確定（[02-screens.md](02-screens.md)）。

## ADR-005: モックは静的HTML・サンプルデータ・切り口別ギャラリーで発散させる

**状態**: 採用 (2026-06)

**背景**: 設計確定前に広く案を出したい。

**決定**: フレームワーク無しの**自己完結HTML**（外部依存ゼロ・オフライン描画）で72案を作り、共通サンプルデータで揃え、`index.html` の**切り口別ギャラリー**（ライブiframeサムネ）で一覧する。並列のサブエージェントで生成。

## ADR-006: 実績時間は TaskStation を fork して DB にネイティブ実装する

**状態**: 採用 (2026-06)。[ADR-002](#adr-002) を一部改訂、[ADR-003](#adr-003) を改訂。

**背景**: 見積りvs実績は必須機能。だが TaskStation に実績時間（worklog）の概念が無い（[04-feasibility](04-feasibility.md) で 🔴 と判定していた）。

**検討した選択肢**:
- **A. タスクコメントを構造化して実績を持つ**（`⏱ 2h · 日付` をパース）— 追加インフラ不要だが、**自由記述コメントと混在し書式ドリフトで破綻する**。DB制約もインデックスも集計の信頼性も無い。**却下**。
- **B. 外部ストア**（Supabase に worklog テーブル）— 堅牢だが TaskStation とデータが分断、二重管理。
- **C. TaskStation を fork し、DB にネイティブな時間トラッキングを足す** — `task_time_entries` テーブル＋`tasks.time_estimate` カラム＋ `/tasks/:task/times` API。データが TaskStation に一級市民として残る。

**決定**: **C（fork して DB に実装）**。実績は `task_time_entries`、見積りは `tasks.time_estimate` 実カラム。

**理由**: 実績時間は制約・集計・権限を伴う**一級のデータ**であり、コメント解析（A）は破綻する。外部ストア（B）は分断。TaskStation は OSS で fork 可能、かつ調査の結果 upstream は既に native time tracking を持つ（idiom 通りに足せる）。fork はこの1機能に閉じ込め、保守は新規3ファイル＋2編集の rebase で収まる。

**結果**: 23/24/42 が 🔴→✅（[04-feasibility](04-feasibility.md) 更新）。設計・適用コードは [05-time-tracking-fork](05-time-tracking-fork.md) と [`../backend-patch/`](../backend-patch/)。`est:4h` ラベル方式（ADR-003）は卒業。

**トレードオフ**: 本家アップグレード時に rebase が要る（fork の宿命）。1機能・小差分に閉じることで許容範囲とする。

## ADR-007: 開発の成熟度モデル「フォーク孵化→検証→昇格」を正式採用（ADR-002 を更新）

**状態**: 採用 (2026-06)。[ADR-002](#adr-002) を更新。詳細は [06-requirements §5](06-requirements.md)。

**背景**: ADR-002 は「TaskStation 本体は触らず API 越しオーバーレイ」を原則とし、ADR-006 で実績時間に限り fork を例外許可した。その後の基盤固めで、**コアの書き込み挙動のバグ（#1: 部分更新で assignees/reminders が消える）は API 越しでは根治できない**ことが判明（[ADR-008](#adr-008)）。開発の進め方そのものを再定義する。

**検討した選択肢**:
- **A. 3ステージ昇格モデルを正式採用** — 機能はまず TaskStation フォーク内で孵化（S1）、フォーク上で動作確認（S2）、証明できたら自前製品・自前UI(SPA)へ昇格（S3）。各ステージに品質ゲート（S1: schema-first＋契約＋unit＋rollback / S2: 隔離e2e＋Playwrightモンキー＋回帰ゼロ / S3: 純関数TDD＋snapshot＋SPA e2e）。
- **B. 現状維持**（fork は時間トラッキングのみの最小例外、以降は API 越し） — #1 のようなコア挙動の問題に対症療法しか打てず、データ破壊リスクが残る。

**決定**: **A**。フォークを「孵化器」と位置づけ、品質ゲートで安全性を担保する。

**理由**: 書き込みの破壊性のようなコア起因の問題はコアでしか根治できず、API オーバーレイの限界が露呈した。フォーク差分は最小・契約テスト付き・rollback 経路つきに閉じ、rebase 追従性（[ADR-002](#adr-002)/[006](#adr-006)）を維持する。

**含意**: コア差分が増えるため rebase 負担は上がるが、各差分は最小・テスト固定に閉じる（[ADR-008](#adr-008) がその実例）。最終的にユーザーが触るのは SPA（オリジナルUI）、TaskStation UI は S2 検証の道具。

## ADR-008: 書き込み破壊性（部分更新で関連が消える）を fork の nil ガードで根治

**状態**: 採用 (2026-06)。

**背景**: `POST /tasks/:id` に `assignees`/`reminders` を含めない部分更新で、既存の担当者・リマインダーが**全削除**される（#1。seed で実際に踏んだ）。根本原因（実コード確認）: `pkg/models/tasks.go` `Task.Update` が L927 `ot.updateTaskAssignees(s, t.Assignees, a)` と L1073 `ot.updateReminders(s, t)` を**無条件**に呼び、payload 不在時 `t.Assignees==nil`/`t.Reminders==nil` のまま `task_assignees.go:80` 等の全削除ロジックに入る。

**検討した選択肢**:
- **A. fork で Update の関連更新を nil ガード**（`if t.Assignees != nil {…}` / `if t.Reminders != nil {…}`）— 「フィールド不在/`null`＝維持、`[]`＝明示クリア、`[{…}]`＝置換」。差分2行＋既存テスト1件の契約更新に閉じる。
- **B. client 側 safeUpdate ラッパ**（get→merge→post＋assignees 復元）— 対症。全 caller に漏れなく適用する保証がなく、レース・往復コスト・reminders 等の取りこぼしが残る。**却下**。
- **C. PATCH 別エンドポイント新設**（presence 追跡）— upstream 乖離が大きく、既存 POST の破壊性も残り根治にならない。**却下**。
- **（検討したが却下）Task に `UnmarshalJSON` を足して presence(不在/null/`[]`)を区別** — `Task` を埋め込む `BulkTask`（一括更新）・`TaskWithComments`（vikunja-fileインポート）でメソッドが昇格し、それらの固有フィールド（`task_ids`/`comments`）が無視されて**壊れる**。将来 `Task` を埋め込む型が増えるたびに静かに壊れる地雷。**却下**。

**決定**: **A（nil ガード）**。

**理由**: 破壊はコアの無条件呼び出しが原因（上記行番号）。コアで直せば全 caller（UI/seed/client/将来の統合）が一律に救われる。最小差分・構造リスクゼロ・rebase 耐性で最も堅牢。`null` は実害なく（SPA は null を送らない、`[]` で明示クリア可能）、`Task` 型・`BulkTask`・`TaskWithComments` には一切触れずに済む。

**トレードオフ**: upstream の `null=クリア` 契約を `null=維持` に変える意図的 fork 仕様変更。`pkg/integrations/task_test.go` の該当テスト1件の期待値を反転し、回帰テスト（#7）で固定する。migration 無し（コードのみ）なので rollback は `git revert` で足りる。繰り返しタスクの done 化では `updateDone`→`setTaskDates*` が `t.Reminders` を非nilに設定するためガードを通過し、再スケジュールは従来通り維持される。

## ADR-009: 予定/実績の帰属は `user_id`=対象者・`created_by`=記録者で持つ

**状態**: 採用・**実装済み (2026-06, #3)**。fork（`user_id`=対象者／`created_by`=記録者・migration 20260610032051）＋計算層（[capacity.js](../app/lib/capacity.js) `toMemberDayEntries`）完了。SPA 配線（フォームの対象者選択・logTime/logPlan の user_id 送信）は次の view パス。

**背景**: `task_time_entries`/`task_time_plans` の「誰の時間か」をどう持つか。現状は作成者(=代理入力した capdemo)に紐づき、人別集計が崩れる。

**検討した選択肢**:
- **A. `user_id`=対象者（その時間を負う人）＋ `created_by`=記録者（入力者）の2カラム明示保持** — 代理入力・自己入力を区別でき、按分はビューで導出可能（可逆）。
- **B. タスク担当者へ按分を正式採用** — 集計は楽だが、誰が記録したか・複数担当時の実配分が失われる（情報欠落）。
- **C. 両建て** — A を持てば按分は導出できるため冗長。

**決定**: **A**。

**理由**: 帰属は一次データとして保持し、按分は導出（集計/ビュー）に回すのが可逆で堅牢。B は情報欠落、C は冗長。

**含意**: #3 で `task_time_entries`/`task_time_plans` に `created_by` を追加（migration 伴う）。それまでは [planner.js](../app/views/planner.js)/[gantt.js](../app/views/gantt.js) のとおり「タスク担当者へ按分」を暫定運用。

## ADR-010: 多担当タスクは全員にフル負荷／会議は多担当タスクで表現

**状態**: 採用・実装済み (2026-06, #4)。

**背景**: 1タスクに複数担当を許す。負荷計算で、見積り/予定をどう人別に配分するか。また「会議」をキャパにどう織り込むか。

**検討した選択肢（配分）**:
- **A. 全員にフル**（按分しない）— 「このセキュリティ設定を各自の環境で」のような**共通作業は各自がフルでこなす**。4h×2人なら各4h。
- **B. 担当者数で按分** — 4h を各2h。実工数合計はタスク値と一致するが、共通作業や会議の実態（各自フル拘束）と合わない。

**検討した選択肢（会議）**:
- **C. 多担当タスクで表現**（専用エンティティ無し）— 参加者=assignees（全員フル）・所要=time_estimate/plans・開催日=due/plan_date・定例=repeat_after・識別=`会議`ラベル。
- **D. fork に会議エンティティを新設** — 日時/長さ/参加者をネイティブ表現。

**決定**: 配分=**A（全員フル）**、会議=**C（多担当タスク流用）**。

**理由**: 共通作業も会議も「関与者全員がその時間を負う」のが実態 → 全員フルが正しい（B は会議の実拘束を過小評価）。会議に必要な要素（複数参加者/所要/日付/定例）はタスクで全て表せ、A の規則により**会議は多担当タスクとして自動でキャパに計上**される。専用エンティティ（D）は車輪の再発明。

**含意**: 計算層から `/aids.length` 按分を全廃（[capacity.js](../app/lib/capacity.js) `toMemberDayEntries`/`taskPlannedHoursByMemberOn`、[planner.js](../app/views/planner.js)）。特定の対象者(`user_id`, [ADR-009](#adr-009)) が付くエントリはその1人にフル。**専用会議エンティティは「時刻帯ブロッキング/出欠/外部カレンダー同期」が要件化したら再 ADR**（現状不要）。

## ADR-011: 定期タスク/会議は RRULE(RFC5545) で持ち、SPA(rrule.js) で展開／祝日・個人休暇で容量を 0 に

**状態**: 採用・実装済み (2026-06, フェーズ5)。

**背景**: 1ヶ月先の「Aが特定日に N時間空き」を出すには、繰り返し（定例タスク/会議）を未来に展開する必要がある。TaskStation 標準の `repeat_after` は**完了時シフト型で未来回を展開しない**＋「毎月第N曜日」等の柔軟ルールを表現できない。祝日・個人休暇も容量に効かせたい。

**検討した選択肢**:
- 繰り返し表現： **A. RRULE(RFC5545)**（`FREQ=WEEKLY;BYDAY=MO`/`MONTHLY;BYDAY=2TU`/`INTERVAL=2` で毎週N曜/毎月第N曜/隔週を網羅） vs B. 自前ルール型（曜日/週/月のフラグ）。
- 展開場所： **C. SPA側 rrule.js**（fork は RRULE 文字列を dumb storage） vs D. fork側 Go(rrule-go) で展開API。
- 会議エンティティ： **E. 多担当タスク/定期で表現**（[ADR-010](#adr-010)） vs F. 専用エンティティ。
- 可用性： **G. 祝日(チーム)＋個人休暇(PTO)** vs 祝日のみ。

**決定**: **A（RRULE）／C（SPA rrule.js 展開）／E（会議＝多担当）／G（祝日＋休暇）**。fork に `recurrences`（RRULE文字列・duration・assignee_ids[JSON]・kind）/`holidays`/`member_unavailability` を新設（dumb storage）。展開・空き計算は SPA（[recurrence.js](../app/lib/recurrence.js)＋ベンダリングした [rrule.mjs](../app/lib/vendor/rrule.mjs)）。occurrence は**仮想**（実タスク/plans 非生成・計画用）。

**理由**: 「使えるライブラリは必ず使う」＝recurrence 計算は RRULE 標準＋rrule.js 一択（自前計算は禁止）。展開は派生データなので計算層([capacity.js])に集約し fork を最小（Go依存追加なし）に。assignee は JSON列で4つ目の表を回避（前例 `api_tokens.Permissions xorm:"json"`）。容量は週末/祝日/休暇を 0 とし、占有が非稼働日に重なれば over（衝突）として可視化。

**結果**: [freefinder](../app/views/freefinder.js)（月次空き）で「毎週月/毎月第2火/隔週/祝日/休暇」が ~5週間先まで (メンバー×日) 空きに反映。S1(go test)→S2(隔離CRUD/migration)→本番 `leo-vikunja:0.24.6-timetracking-fix4`→seed→Playwright で確認済。

**トレードオフ**: occurrence は仮想なので、定期の「実績/完了」追跡は別途 materialize が要る（将来）。時刻帯ブロッキング（時間単位）は日次粒度の本モデル外（要件化したら再 ADR）。rrule.js は ESM を依存インライン化して単一ファイルにベンダリング（buildless維持）。

## ADR-012: 「種別(kind)」と「時間属性(当日追加/前倒し)」を別軸にする／種別の保存はラベル規約／「本日にやる＝plan」を真実源と明文化

**状態**: 採用・実装済み (2026-06)。SPA計算層のみ（フォーク/スキーマ変更なし）。

**背景**: 「本日の稼働予定・円時計」と「レビュー」を実装する中で、種別(会議/定例/レビュー/予定タスク/当日追加)を [today_items.js](../app/lib/today_items.js) の **単一 enum `cat` に詰め込んだ**結果、本来 直交する概念が衝突した。例：**本日作成のレビュータスクは `review` か `adhoc` の択一**になり、「種別=レビュー かつ 当日追加」を表現できない。また 種別の判定が（`recurrences.kind` / ラベル / `created`日付）と散らばり、表示定義（色/模様/並び）が clock.js と review.js に重複していた。「データ構造はエレガントか／無理やりやってないか」という問いを機に棚卸し。

**検討した選択肢（モデル）**:
- **A1. 単一 `cat` enum に種別＋時間属性を混在**（旧実装）— 実装は速いが直交概念が択一になり破綻。
- **A2. 2軸：`kind`（種別・単一軸）× `flags`（時間属性: adhoc/advanced）**（採用）— 「レビュー×当日追加」等の併存を自然に表現。
- **A3. tasks に `kind` カラムを新設**（フォーク変更）— 会議/定例は tasks でなく recurrences 由来なので一貫させられず、スキーマ追加も過剰。

**検討した選択肢（種別の保存）**:
- **B. 会議/定例=`recurrences.kind`、レビュー=ラベル「レビュー」、通常=無印**（採用・[ADR-010](#adr-010) の `会議`ラベル方針と一貫）。タスク側の種別は **ラベル規約** で持つ（Vikunjaネイティブ・スキーマ不要）。「当日追加」は**型ではなく `created` 由来の派生属性**（保存しない）。
- vs B'. タスクに種別カラム/専用テーブル（却下：車輪の再発明）。

**検討した選択肢（"本日にやる" の真実源）**:
- **C. `task_time_plan`(plan_date) を正準**とし、`due`/`start-end` は「締切と幅」であって稼働日ではない、と明文化（採用）。plan の無いタスクは見積り日割りの**暫定表示**。
- vs C'. due/期間も対等に稼働日として扱う（却下：本日負荷に複数の真実源ができ、move 操作が plan系/期日系に分岐して複雑化した実例あり）。

**決定**: **A2（2軸 kind×flags）／B（ラベル規約で種別保存）／C（plan を本日の真実源と明文化）**。表示トークン（KINDS=ラベル/模様/並び順、PRIO=優先度色、isReviewTask）を新規 [kinds.js](../app/lib/kinds.js) に一元化。WorkItem は `{kind, prio, flags:{adhoc,advanced}}`。[clock.js](../app/views/clock.js) は kind=セクション/模様、当日追加=ピン＋「当日」タグ、前倒し=タグ として **kind と重ねて描画**。

**理由**: 種別と時間属性は直交（レビューでも当日追加でありうる）→ 軸を分けるのが素直。種別保存はラベル規約で十分（[ADR-010](#adr-010)と一貫・フォーク不変）。「本日=plan」を一本化すると move 操作（別日へ移す）の二分岐の根本原因が消える方向に揃う。

**含意 / トレードオフ**: 今回は **計算層の正規化と明文化に留め**、(1) plan への完全一本化（due/範囲ベースの暫定表示の廃止）と (2) 定期 occurrence の materialize（[ADR-011](#adr-011) で将来保留）は**据え置き**。move は当面 plan系/期日系の二分岐を温存。これらは「定期の実績/完了を追う」「本日表示の挙動を統一する」要件が出たら次ADRで着手。検証: [today_items.test.mjs](../app/lib/today_items.test.mjs) に「レビュー×当日追加＝`kind:review, flags.adhoc:true`」を追加（35件 green）、leo:7010 Playwright で円時計の併存表示を確認。
