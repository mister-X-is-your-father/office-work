# 統合プロトタイプ計画

> status: ドラフト。72案の発散を、1つのアプリ（サイドナビ＋画面遷移）に収束させるための計画。
> 目的: バラバラのモックを「触って行き来できる1つのプロトタイプ」にする。

## 0. ゴール段階（3フェーズ）

| フェーズ | 内容 | データ | 成果物 |
|---|---|---|---|
| **P1 統合プロト（静的）** | 選定モックを1つのSPAに束ね、サイドナビ＋画面遷移で行き来できる | サンプル（ダミー）共通 | クリック可能な叩き台 |
| **P2 実データ（読み取り）** | Vikunja API に接続し、実データでキャパ/着地等を表示 | Vikunja REST（読み取り専用） | 動く社内ツール |
| **P3 双方向** | アサイン変更・est編集などを Vikunja に書き戻し | Vikunja REST（書き込み） | 運用ツール |

まず **P1** を作る。スタック決定や API 接続は P1 を触ってから。

## 3. 技術スタック（P1 の選択肢）

| 案 | 中身 | 向き |
|---|---|---|
| **A. 単一HTML/Vanilla** | 既存モックをそのまま `<iframe>` or コンポーネント化、ハッシュルータで切替 | 一番速い。モック資産を最大流用。P1の叩き台に最適 |
| **B. Vite + React/TS** | モックをReactコンポーネント化、状態共有 | P2(API接続)に繋げやすい。やや手間 |
| **C. Next.js + Supabase** | 既存 manademia 基盤に寄せる | P2/P3まで見据えるなら本命。最初は重い |

**推奨**: P1 は **A（最速で触れる形）** で叩き台 → 方向確定後に **B/C** へ移植。
共通サンプルデータを1つの JSON に集約し、各画面がそれを読む形にしておくと P2 で API 差し替えが楽。

## 4. データモデル（P1 の共通サンプル → P2 で Vikunja にマップ）

P1 で使う共通サンプルを `data/sample.json`（仮）に集約する想定:

```jsonc
{
  "today": "2026-06-04",
  "members": [{ "id":"morita","name":"森田","capacityH":8 }, ...],
  "tasks": [{
    "id":"t1","title":"API設計","assignee":"morita",
    "project":"Backend","estH":4,"start":"2026-06-02","end":"2026-06-04",
    "status":"done","progress":100,"priority":"high","deps":[]
  }, ...]
}
```

P2 でのマップ（Vikunja → 本モデル）:
| 本モデル | Vikunja |
|---|---|
| task.assignee | task.assignees |
| task.estH | **ラベル `est:4h` をパース**（[ADR-003](01-decisions.md)） |
| task.start/end | start_date / end_date |
| task.status | done フラグ＋bucket（kanban列） |
| task.priority | priority |
| task.deps | related_tasks（依存） |
| member.capacityH | 一律 8（将来：人別設定） |

キャパ計算（空き=容量−Σest、超過、着地予測）は**自前レイヤー**で。

## 5. 次のアクション

1. **画面選定の確定** — [02-screens.md](02-screens.md) を見て、各ナビ枠の採用案を1つに決める（54は確定）。
2. P1 を **案A** で組む — サイドナビ＋8画面＋共通サンプルJSON。
3. 触って画面/遷移を調整（ここで残りの切り口も流し込む）。
4. Vikunja インスタンスを1つ立て、P2（読み取り接続）へ。

> まず 1（選定）を済ませれば、2（統合プロト P1）に着手できる。
