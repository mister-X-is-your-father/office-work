## モデル（確定）

```
プロジェクト（必須・親タスク）
  ├─ タスク                      ← グループ無しで直下もOK（2段）
  └─ タスクグループ（任意・中間の親タスク）  ← ミドルネーム的に、有っても無くてもいい
        └─ タスク                ← グループ下のタスク（3段）
```

- **「プロジェクト ＞ ［タスクグループ：任意］ ＞ タスク」**。グループを挟めば3段、挟まなければ2段。**両方が正規**。
- **タスクグループ＝構造上は親タスク**（プロジェクトと同じく子を持つ親タスク）。新エンティティではなく、parenttask 鎖の中間ノード。
- **ワークスペース(=Vikunja project)は"箱（スコープ）"であり階層レベルではない**（一覧に階層として出さない）。「3層」はあくまで タスクの木（プロジェクト＞グループ＞タスク）で数える。

## STEP1 土台（なぜ・どこまで）

- **目的(Why)**: プロジェクト直下にタスクを並べるだけだと、規模が大きいプロジェクトで分類できず埋もれる。**任意の中間グループ**でタスクを束ねられるようにし、整理と一覧性を上げる。
- **現状(As-Is)**: 一覧（table）が見せる階層は「プロジェクト ＞ タスク」の2段。中間グループの概念がUIに無い（データ上は parenttask で3段ネスト可能だが、作成導線も命名も2段前提）。
- **ゴール(完了条件/To-Be)**: 「プロジェクト ＞ タスクグループ（任意）＞ タスク」が**標準の操作モデル**として成立。具体的には:
  1. プロジェクト直下に「タスクグループ」と「タスク」を、グループ直下に「タスク」を**自然に作成できる**。
  2. 一覧/アウトラインで**任意グループが段付きで見える**。
  3. kanban/一覧の「プロジェクト」列が、グループ有無に関わらず**最上位プロジェクトを正しく指す**（祖先解決・実装済）。
  4. UI表記が「プロジェクト/タスクグループ/タスク」で統一。
- **やること**: 作成導線・命名/見分け・一覧表示・kanbanのグループチップ。
- **やらないこと（★）**:
  - ワークスペースを階層レベルに昇格させない（WSは箱のまま）。
  - **4段以上（グループ＞グループ）の正式サポートはしない**。深くしても祖先解決ガードで「最上位プロジェクトに集約」して崩れない劣化対応のまま（[task-group は1段だけが標準]）。
  - **データ移行はしない**。既存タスクは2段のまま、グループは任意で後付け。
- **関係者(Whom)**: 利用者=森田(id7)／実装=指示役＋画面サブエージェント（capacity-dashboard 委譲規約に従う）。
- **前提・制約**: parenttask 3段ネストは実証済（P>T>G で API 受理・読み戻し確認）。祖先解決ガード `projectAncestor` は commit `9891297` で merged 済（kanban/triage のプロジェクト列に適用）。
